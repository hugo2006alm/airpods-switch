# ADR-001: Independent managed core with isolated Windows and L2CAP transport

Status: **Accepted** for diagnostic MVP; live transport compatibility is hardware-gated.
Date: 2026-10-15. Evidence: [feasibility](FEASIBILITY.md), [protocol](AACP_SWITCHING.md).

## Context and drivers

Required order: Bluetooth primitive access, correctness, diagnostics, maintainability.
AACP is Classic L2CAP. The audited Tblob18 Qt application requests L2CAP through a
Windows backend that only accepts RFCOMM. Changing UI language cannot bypass this.
Windows has a documented kernel profile-driver L2CAP path; user mode can communicate
with a compatible installed driver through device interfaces and overlapped I/O.

## Options

| Option | Bluetooth / L2CAP | Media, audio, notifications | Complexity, packaging, reliability, reuse/license |
|---|---|---|---|
| A: C++ + Qt 6 | BLE available; Windows Qt raw Classic L2CAP unavailable; driver still required | Native adapters needed; existing media watcher is stub | Qt/OpenSSL deployment, inherited reconnect and placeholder risks; small GPL protocol modules reusable; no transport advantage |
| B: C++/WinRT + Windows App SDK | WinRT BLE/RFCOMM, driver still required for PSM 0x1001 | Direct GSMTC/Core Audio/App SDK access | Good native integration; more lifetime/build/packaging work; GPL adaptation possible; appropriate for future kernel boundary work |
| C: C#/.NET plus isolated native interfaces | P/Invoke radio discovery/SetupAPI; WinRT BLE; compatible driver via async device file | GSMTC and Core Audio accessible; WinForms tray; App SDK notification adapter | Small testable immutable core, easy JSON diagnostics/registry backup, self-contained Windows deployment; requires .NET runtime or bundled runtime; GPL-compatible project |
| D: Electron/Python UI | Same driver constraint | Additional bridges/runtimes | No primitive-access advantage; adds deployment/process complexity; reject for this diagnostic MVP |

## Decision

Choose **C**: .NET 10, pure core assembly, separate Windows integration assembly,
diagnostic CLI, deterministic test project, and minimal tray host. Pin SDK/dependencies.
Use supported Win32 APIs for Bluetooth radios and paired devices, SetupAPI for an
installed AAP profile driver, WinRT GSMTC for meaningful media, and Core Audio for render
sessions. No undocumented IPolicyConfig output switching. User selects the audio route
through Windows; app observes it and refuses unproven route success.

Native ABI operations sit behind `BluetoothTransport`, `WindowsMediaMonitor`,
`WindowsAudioManager`, `NotificationManager`, and registry-store interfaces. P/Invoke is
sufficient for current user-mode native calls; do not add an empty C++ DLL. A production
profile driver, if needed, is a separate WDK/C++ component and requires a later ADR
covering signing, device binding and supported adapters. No kernel binary is installed
or generated by the application.

Adapt only protocol layouts/model data and a small driver-interface transport. Preserve
GPL-3.0-or-later notices and exact source mapping. **Keep the standalone repository.**
No overwhelming justification exists for inheriting either complete upstream repository.
Do not fork Android, vendor upstream apps, or change repository strategy implicitly.

## Consequences

Software parsers, policy, DID backup/restore, media diagnostics, tray status and protocol
replay can be built/tested now. Live AACP requires a compatible installed profile driver
and physical confirmation of framing, identity and routing. Driver absence produces a
specific unavailable result; never fall back to RFCOMM or blind reconnect. A compatible
driver's existence alone does not certify its signature or safety.

Application state has one serialized owner, immutable snapshots, monotonic observation
times, transport epochs, bounded I/O/deadlines and one pending takeover. Notifications
only carry request IDs/actions; coordinator rechecks eligibility on acceptance. DID
mutation is independent and never invoked by the tray. Android bridge remains deferred.
